# Deployment status and gates

The existing [root deployment guide](../DEPLOYMENT.md), [VPS setup](../VPS_SETUP.md), [backup/restore](../BACKUP_RESTORE.md), [migration](../MIGRATION_PLAN.md) and [rollback](../ROLLBACK_PLAN.md) are procedures awaiting execution evidence. No VPS was purchased or provisioned. No production deployment was performed.

Target one 2-vCPU/4-GB Ubuntu LTS server, no GPU, Compose API/PostgreSQL/Caddy. One modular authority serves every plan. PostgreSQL is private, persistent volume required; production override removes API host port, uses read-only API filesystem/non-root process, HTTPS reverse proxy. Stable API domain and environment configuration permit later migration. No customer capacity guarantee exists.

Before any production deployment: reject mock/placeholders; bind private secrets; verify actual PostgreSQL migrations/transaction behavior; restore an encrypted off-server backup into a disposable database and compare balances/rows; configure schedule/retention/alerts; exercise graceful shutdown and restart/unknown inference reconciliation; test TLS/firewall/SSH keys; measure latency/RAM/disk/load. Dependency notices and patching remain operator duties. Current Compose lacks explicit application log rotation/resource quotas and monitoring collection; implement and test those before customer operation.

Capacity threshold code accepts synthetic samples only; it is not a deployed monitoring dashboard. Proposed sustained warnings CPU75%, RAM80%, disk80%, latency target configurable. Actual request/error/database/AI spend and license-failure metrics need collection, retention and alert delivery. Scaling is administrator-approved, never automatic paid provisioning.

Gateway admission follow-up: `NIGHTBREW_GATEWAY_MAX_CONCURRENT` defaults to 2 and `NIGHTBREW_GATEWAY_ACCOUNT_MAX_CONCURRENT` to 1; both accept integers 1–128. Admission counts `inference.status='reserved'` inside the same serialized transaction as credit reservation, so separate API processes share slots. A saturated request returns 429 before debit or provider dispatch. Completed and handled unknown-outcome requests release their slots; unknown billing retains its money reservation and request ID cannot replay. A process crash leaves a reserved slot fail-closed. Before manually reconciling such a row, drain/stop dispatch and verify the provider outcome; do not delete the row, refund blindly or expire it automatically. An operator reconciliation UI/job is still absent. Actual PostgreSQL cross-process behavior requires integration tests.

Stage 2 migration requires backup verification, write freeze/draining, version checks, transfer/restore, consistency checks, controlled traffic switch, health/monitoring and a rollback cutoff. Prevent split writes while DNS propagates. Once new writes occur, restoring the old server blindly loses data; reconcile or forward-recover first. Stage 3 is design only until load warrants separate database/API replicas/workers.
