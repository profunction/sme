# Security boundaries and remaining release work

The desktop API binds loopback only and requires a high-entropy bearer session on data routes. Electron generates a fresh token/instance ID, authenticates its own child before exposing the session through validated main-frame IPC, and does not reuse/kill unrelated services. Renderer sandbox/context isolation are enabled, Node access is disabled, CSP limits scripts/connect destinations, and new windows/navigation/permission requests are denied. IPC exposes session and opt-in updates, not arbitrary commands/filesystem access.

AI output, extracted documents and connector/browser content are untrusted data. They never grant permissions, auto-approve tasks or execute code. There is no unrestricted shell, arbitrary browser JavaScript, coordinate click fallback or AI-generated Python execution. Browser/Windows plans are explicit bounded user-reviewed steps. All computer actions, connector writes and deletion require exact-task approval; employee tool/connector permissions and immutable snapshots are rechecked before execution. Changes invalidate pending assignments. Local authenticated session holders are administrators; employees are scoped application identities, not separate OS users or a multi-tenant login system.

Cloud inference requires explicit global permission and per-message consent, and private tasks never go to cloud. HTTPS verification remains enabled; credentials are not forwarded through redirects. Windows cloud/account BYOK uses native Credential Manager without plaintext fallback; Linux cloud uses configured environment bindings. Never put tokens/passwords in stored automation plans. Password form filling is rejected; secure credential-reference login automation is not implemented. A fresh browser context does not reuse a customer's authenticated browser profile. Browser destinations are allowlisted, writes default off, and popups/downloads/service workers/websockets are blocked. Egress controls must also prevent private routing/DNS rebinding; an administrator host allowlist is not a standalone DNS firewall.

Local file APIs accept only registered IDs under a private data directory. Formulas/macros are not executed. Office archives and extraction sizes have bounds. Uploaded business content, task payloads, screenshots and local SQLite are plaintext under OS account permissions; encrypted-at-rest storage, malware scanning and native parser process isolation remain release requirements. Cancellation/timeouts are cooperative and cannot undo in-flight actions. Interrupted work is never auto-replayed; externally ambiguous writes require manual reconciliation. Logs rotate and omit tokens, headers, payloads and prompts; audit events use IDs/types only.

Production license/public update policy is embedded by the build. Packaged mode forcibly enables signed licensing and rejects mock grants/authority secrets inherited into the child. The separate billing authority holds Ed25519 signing keys, merchant/provider keys, customer credentials, paid balances and online quotas. Local editable SQLite cannot prove payment or create a valid signature. Signed grants are device-bound and short-lived; online quota checks reject inactive subscriptions. No tamper-proof DRM, trusted local clock or device identifier immune to a machine administrator is claimed. Protect authority storage, backups, TLS, keys and administrator access separately.

Stripe webhooks check signatures/timestamps, known checkout sessions, event/invoice idempotency and canonical subscription state. Mock confirmation is administrator-only and disabled in Stripe mode. Unknown inference billing retains its reservation. Included company-provider credits are consumed on the trusted gateway, not asserted by a desktop receipt. BYOK/local budgets are additional controls, not authoritative paid credits.

Production packaging fails without public authority configuration, HTTPS update feed and code signing credentials. Updates are user-requested, publisher-verified and not auto-installed on quit. Unsigned CI artifacts are explicitly development-only. Code signing, live merchant/gateway validation, Windows integration results, secure hosting, abuse controls and customer acceptance remain prerequisites for production distribution. Linux headless Electron tests disable the OS sandbox only for that test process; they do not validate Windows OS sandbox enforcement or signing.
